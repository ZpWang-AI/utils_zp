# Issue Notes

本文件用途：记录本仓库修 issue 场景下的 issue、待确认问题、后续 TODO 和处理建议，便于多个 agent 或后续接手者持续追加。

## 记录约定

- 适用场景是 issue 排查、issue 修复和 review 发现后的问题跟踪；正常开发流程统一走 `.agent/PROGRESS.agent.md`
- 优先记录“会影响正确性、可运行性、可维护性”的问题
- 每条 issue 尽量写清：现象、影响范围、复现线索、建议动作
- 所有事项统一记录在 `TODO` 下，使用 `1. 2. 3.` 编号列表，不使用 `-` 列表
- issue 条目推荐格式为：`1. 标题（摘要）`，下面固定写 `标签：`、`问题：`、`代码：`、`建议方案：`、`解决时间：`、`解决方案：`。
- `标签：` 统一写成 `优先级=P0/P1/P2/P3；问题类型=...`；`问题类型` 优先用简短中文短语，例如 `正确性`、`可运行性`、`流程规范`、`可维护性`、`文档`、`兼容性`。
- 未完成条目的 `解决时间：` 与 `解决方案：` 先写待补充说明；已完成条目补实际落地方案，并填写精确到秒的 `解决时间：YYYY-MM-DD HH:MM:SS`。
- `建议方案` 必须使用内联写法，例如 `建议方案：1. ... 2. ...`；不要在下一行另起 Markdown 编号列表，以免和外层 `TODO` 的 `1. 2. 3.` 编号混淆。这里的 `1. 2. 3.` 表示可选方案，不表示实施步骤；如果只有一个合理方案，就只写 `1.`。
- 每条事项的标题或摘要里直接标注状态，例如 `（已完成）`、`（待处理）`、`（进行中）`、`（待确认）`
- 开始修 issue 时，优先直接把对应 issue 条目标成 `（进行中）`；只有需要额外同步过程状态、临时约定或交接信息时，才在 `.agent/PROGRESS.agent.md` 中补对应的进行中记录
- 如果用户明确要求归档，已归档条目统一移动到 `.agent/issue_archive/`
- issue 归档按日期组织；归档文件名统一使用条目 `解决时间` 所属日期，格式为 `YYYY-MM-DD.md`
- 归档时必须保留原始条目序号；归档文件中的条目序号保持原号，主 `ISSUE.agent.md` 里剩余 TODO 也保持原号，不因删除已归档条目而重排
- 如果 issue 排查期间仓库状态发生变化，先注明基于哪个目录状态或时间点得出的结论

13. YAML fallback 修复会误改 `detail_markdown` 中的 markdown 正文（待处理）
标签：`优先级=P1；问题类型=正确性`
问题：基于 2026-08-04 当前 staged 代码状态，`src/utils_zp/cli/_yaml_index.py` 新增的 `_quote_markdown_plain_scalars()` 会在 `yaml.safe_load()` 失败后，对全文所有包含 `: \`` 的行做字符串级重写。这样虽然能把 `summary: \`zpdata 10\` ...` 这类非法 plain scalar 修成可解析 YAML，但也会误处理 `detail_markdown: |` 这类 block scalar 里的普通 markdown 行。例如同一份 YAML 中若同时出现非法 `summary` 和正文 `- path: \`exp/01\``，fallback 后正文会被改成 `- path:  \"\`exp/01\`\"`；进一步在 `mark/unmark` 等“读入再写回”路径中，这种误改会被持久化回索引文件，造成详情正文被静默污染。
代码：`src/utils_zp/cli/_yaml_index.py`
建议方案：1. 不要对整份文本做逐行无上下文替换，改为只在明确的目标字段上做最小修复，且跳过 block scalar 内容。2. 为包含 `detail_markdown: |` 和反引号行的混合 YAML 补最小回归测试，覆盖“仅读取”和“读取后写回”两条路径。3. 如需继续做文本级容错，至少先按 YAML 结构或缩进态跟踪当前是否处于 block scalar，避免误改 markdown 正文。

# Jobs Entry

说明：这里放可直接分配给 agent 的工作清单，按工作类型分流；具体 repo 事实仍以当前文件状态和产物为准。

- 如果用户说 `jobs`，先列出本文件支持的工作类型，再让用户明确选一个交给 agent 做；在用户选择前，不默认直接开始其中某项工作。
- 某类工作如果在具体 repo 内还有额外口径，优先先按本文件选工作，再到对应 repo 的 `.agent/JOBS.agent.md` 看该仓补充约定。

## 1. commit message

- 只根据 `staged` 改动整理 commit message，不执行 `git commit`。
- 以 `staged` 内容为主，`.agent/PROGRESS.agent.md`、`.agent/ISSUE.agent.md` 及 archive 只补背景。
- 如果同时有 `staged` 和 `unstaged` 改动，要明确说明提交说明基于哪一部分。
- 默认用中文，可按需采用 `feat`、`fix`、`refactor`、`docs`、`test`、`chore` 风格。

```text
feat: 新增 zprules 命令并整理 agent 文档入口

- 新增 zprules CLI，用于直接输出 agent_zp/README.agent.md
- 调整 agent_zp 文档结构，拆分 workspace entry 与 jobs 入口
- 同步更新相关说明，统一入口命名和职责边界
```

## 2. agent 文档归档

- `gd` 默认表示归档当前 workspace 下各 repo 的 `issue` 和 `progress`。
- 归档前先读主文档，再读相关 archive。
- `issue` 按 `解决时间` 归档，`progress` 按 `实现时间` 归档；文件名统一为 `YYYY-MM-DD.md`。
- 默认保留原始序号；只有用户明确要求或已发生冲突时才重编号。

## 3. 项目文档整理

- 触发场景：用户要求整理某个 repo/目录的 README、`.agent` 入口、目录说明或长期文档口径时。
- 先整体通读，再统一整理，不只改局部字句。
- 优先删重、补缺、统一结构；保证内容完整的情况下追求精简。
- 根入口优先做“导航 + 分流 + 硬约束”，把背景和细节下沉到子文档。
- 如果改动落在某个 repo 内，且涉及长期保留的 README、`.agent` 入口或目录说明，完成后在该 repo 的 `.agent/JOBS.agent.md` 记一下：这次做了什么、最近一次时间。

## 4. history 总结

- 触发场景：用户要求整理 history、抽取长期规则，或区分“该沉淀什么”“该归档什么”时。
- 先区分“可长期复用的经验”和“仅用于回溯的过程记录”。
- 可长期复用的内容回填到对应 `README.agent.md` 或专题文档。
- 只剩回溯价值的历史文档归入 `agent_zp/history/archive/`。
- 如果总结内容被沉淀成某个 repo 的长期约定或固定入口，再在该 repo 的 `.agent/JOBS.agent.md` 记一下：这次沉淀了什么、最近一次时间。

## 5. 阶段总结 / 交接

- 优先回答五件事：用户要什么、实际做了什么、当前状态、下一步、先看哪些入口。
- 结论以当前文件状态和当前产物为准；未重新核实的内容不要写成确定事实。
- 做入口整理类总结时，优先写清分流结果，不堆平级路径。

## 6. 查看运行状态

- 触发场景：用户要求判断训练、评测、数据处理或实验任务是否还在运行、是否已成功或失败时。
- 先看 `_RUNNING`、`_FAILED`、`_SUCCEEDED` 标签，再复核日志或 summary 是否仍在变化。
- 不要只靠当前机器的进程列表或 GPU 状态判断任务是否仍在运行。
- 输出时区分：仍在推进、运行标签残留、已明确失败/成功。
- 如果这次检查形成了后续复用的观察口径、排查模板或长期运行结论，再在对应 repo 的 `.agent/JOBS.agent.md` 记一下：这次确认了什么、最近一次时间。

## 7. 清理无用文件

- 适用场景：清理 `tmp/` 下过期的无用文件，或清理 `outputs/` 下明确无用的 `dryrun` 产物。
- 先列候选文件，再删文件；不要一上来直接批量 `rm`。
- 对 `tmp/`：优先清理明显过期、最近无更新、且不再用于排查或交接的日志、临时脚本和中间产物。
- 对 `outputs/`：默认只清理名称、路径或上下文里能明确判断为 `dryrun` 的临时产物；正式结果、来源不明文件、最近仍在变化的文件不默认删除。
- 删除前必须核对三件事：1. 没有 `_RUNNING` 等运行标记仍指向该目录；2. 相关日志、manifest、README 或脚本里没有继续引用该路径；3. 候选文件最近时间戳不再变化。
- 如果存在“看起来像无用，但不能 100% 确认”的文件，先把候选清单和判断依据给用户确认，再执行删除。
- 删除后要回报：删了什么、为什么判定可删、是否有刻意保留的高风险文件。
- 如果实际清理落在某个 repo，且这类清理后续还会重复发生，完成后在该 repo 的 `.agent/JOBS.agent.md` 记一下：这次清理了什么、最近一次时间。

## 8. code review

- 触发场景：用户要求 review 某次改动、某个模块、某组脚本范围，或要求继续排查仓库问题、做全面巡检时。
- 以 code review 方式审查改动，优先找 bug、风险、行为回归和缺失测试。
- 结论先给 findings，再给简短总结；如果没有 findings，要明确说“未发现明确问题”，同时补充残余风险或测试空白。
- review 时重点留意“语义分散”和“隐藏默认值”两类问题，例如同一配置字段在多处重复解析、或底层库默认行为悄悄改写业务数据。
- 对已确认会影响正确性、可运行性或数据口径的问题，要明确沉淀为可跟踪 issue，不要只停留在口头提醒。
- 如果 review 范围落在某个 repo，完成后在该 repo 的 `.agent/JOBS.agent.md` 记一下：这次 review 做了什么、最近一次时间；如发现明确问题，再同时写入该 repo 的 `.agent/ISSUE.agent.md`。

## 9. 训练/测试任务

- 先问用户这次是否真的要跑 GPU；如果要，必须确认使用哪块物理 GPU。只是在当前仓整理命令、脚本、配置或 smoke test 时，不默认直接执行耗时 GPU 命令。
- 先检查模型、训练脚本、评测脚本和相关配置是否能串起来；发现明确问题先修复，再继续给命令。
- 如果缺少合适的薄包装脚本、测试入口或复用模板，可以补一个最小可维护版本，但不要为了“有脚本”再套一层无意义包装。
- 至少做一轮小测试，优先选源码直跑、dummy/smoke、`--help`、轻量回归或最小配置检查，避免把未经验证的命令直接交给用户。
- 结束时在对应 repo 的 `tmp/` 下写一份 shell，内容至少包括训练/评测命令、关键参数、日志落盘路径、产物核对点；然后把 shell 路径明确发给用户。
- 如果这次工作落在某个 repo，且顺手补了长期可复用的训练/测试口径，完成后在该 repo 的 `.agent/JOBS.agent.md` 记一下：这次做了什么、最近一次时间；如发现明确缺陷，再同时写入该 repo 的 `.agent/ISSUE.agent.md`。

## 10. 整理实验结果

- 触发场景：用户要求查看 `outputs/` 下实验进度和结果、把稳定结果整理到 `exp_reports/`，或补写实验总结与相关说明文档时。
- 先核对运行状态，再整理结果：优先看 `_RUNNING`、`_SUCCEEDED`、`_FAILED`、`_INTERRUPTED` 等标记，以及 `metrics.json`、`predictions.jsonl`、`trainer_state.json`、summary 或日志时间戳，避免把仍在变化的实验误当成最终结果。
- 只把确认可复用、可复核的结果沉淀到 `exp_reports/`；目录命名优先使用 `YYYYMMDD_short_topic`，并按现有约定补 `docs/README.md`、`docs/leader_summary.md`，需要时再补 `docs/analysis.md`、`artifacts/`、`support/`。
- 文档撰写要以真实产物为锚点：结论、指标、显著性分析和基本 sanity check 要能回指到实际输出，不只写口头判断。
- 如果这次整理改变了实验入口、报告索引、同步方式或长期口径，再同步更新对应 repo 的 `README.agent.md`、`README.md`、`.agent/README.agent.md` 或 `.agent/JOBS.agent.md`。
- 如果过程中发现结果异常、口径不一致、产物缺失或明显 bug，先明确写成对应 repo 的 `.agent/ISSUE.agent.md`，不要只停留在实验报告里。

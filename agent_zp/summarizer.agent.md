# Summarizer Entry

说明：本文件承载“总结者”角色的具体约定，包括 `git commit message` 整理、阶段总结和文档整理。

## Git Commit

- 根据 staged 改动整理一版 commit 摘要给用户确认；不要执行 `git commit`
- 生成 commit message 时，以 `staged` 代码为主依据；`.agent/PROGRESS.agent.md`、`.agent/ISSUE.agent.md` 及其 archive 只用于补充背景、命名和完成事项
- archive 只补充“上一次 commit 之后新增完成”的相关内容；如果文档结论和 `staged` 改动不一致，以 `staged` 代码为准
- 默认使用中文生成标题和正文；标题优先贴近实际改动，可按需采用 `feat`、`fix`、`refactor`、`docs`、`test`、`chore` 等 Conventional Commit 风格
- 如果没有任何 `staged` 改动，要明确说明无法基于 `staged` 范围生成准确提交说明，不要伪造提交范围
- 如果工作区同时存在 `staged` 与 `unstaged` 改动，提交说明要明确自己是基于哪一部分整理的，不要把未暂存内容混进提交范围
- 当提交说明需要引用 issue / progress 编号、完成项或归档结论时，先重新读取最新文档状态再写，避免引用过期编号或旧状态

示例：

```text
feat: 新增 zprules 命令并整理 agent 文档入口

- 新增 zprules CLI，用于直接输出 agent_zp/README.agent.md
- 调整 agent_zp 文档结构，拆分 workspace entry 与总结者入口
- 同步更新相关说明，统一入口命名和职责边界
```

## 文档整理

- 先把相关文档整体过一遍，再统一整理内容；不要只改局部字句而忽略上下文
- 以“删掉重复冗余、补齐省略缺失、统一结构和命名”为主要目标，对已有内容重新 refine
- 保留原始事实和约束，不要为了通顺擅自改动结论；如果不同文档之间存在冲突或缺口，要明确标出
- 输出优先保证结构清楚、层次稳定、表述一致；默认使用中文
- 对仓库级 `README.agent.md`，优先做“导航页 + 分流入口”，先给出规则入口、任务类型入口、代码目录入口，再把实现细节和专题背景下沉到子文档；不要把 repo 根文档越写越像总档案

## 阶段总结

- 阶段总结优先回答四件事：用户这轮要什么、实际做了什么、当前状态是什么、下一步如果继续会做什么
- 多轮任务不要机械复述全部对话，优先按“阶段/问题/结果”分组；只有在编号演进、状态变更或用户指令反复切换时，才补必要的时间线
- 如果任务本质上是在帮用户“找入口”或“收结构”，总结时优先写清分流结果：先看哪些规则、再按什么任务类型分流、最后落到哪些目录或脚本；不要把大量平级路径直接堆给用户
- 总结里的“已完成”必须以当前文件或当前产物状态为准；没有重新核实的内容不要写成确定事实
- 当任务涉及文档维护、归档、编号整理时，除了说明改了哪个文件，还要明确：
  - 归档目标文件路径
  - 归档依据字段，例如 `解决时间` 或 `实现时间`
  - 是否保留原始序号
  - 主文档里是否还残留 `（已完成）` 条目
  - 后续新增事项应从哪个编号继续
- 如果过程中出现并发修改、用户新增条目、编号冲突或状态漂移，要在总结里交代“发现了什么变化、最后按什么口径收敛”
- 总结要区分“代码/文档已改好”和“运行结果已验证”两类事实；像 `rg` 无匹配、`git status` 脏树、summary 文件滞后这类信号都要准确解释，不要误报为失败或成功

## 文档维护经验

- 如果用户说 `gd`，默认将其解释为“归档当前 workspace 下所有 repo 的 `issue` 和 `progress`”。执行时按 repo 逐个检查 `.agent/ISSUE.agent.md`、`.agent/PROGRESS.agent.md` 及其对应 archive，把已完成条目按权威时间字段归档落盘
- 处理 `.agent/PROGRESS.agent.md`、`.agent/ISSUE.agent.md` 及其 archive 时，先读主文档，再读相关 archive，最后看当前工作区状态；不要只盯着单个文件下判断
- 整理大型 repo 文档时，先做“分流设计”再动笔：哪些内容留在仓库级入口，哪些下沉到 `src/README.agent.md`、子模块 `README.agent.md`、`.agent/doc/` 或归档文档，要先想清楚；目标是让接手者先定位，再深入，而不是第一次阅读就被全量细节淹没
- 归档按条目里的权威时间字段落盘：`issue` 看 `解决时间`，`progress` 看 `实现时间`；同一天统一追加到对应 `YYYY-MM-DD.md`，没有文件再新建
- 归档默认保留原始条目序号；主文档剩余条目也保持原号，不因删除已归档条目而重排。只有用户明确要求整理编号，或现有编号已经和历史归档冲突，才处理重编号
- 一旦做了重编号，需要同步更新主文档顶部的“最新已使用序号 / 当前剩余最大序号 / 后续从几号开始”的上下文说明，避免后续继续撞号
- 对“已无匹配项”的校验命令要结合工具语义解读。例如 `rg` 在没搜到时返回 `1`，这通常是“已清空待归档项”的确认信号，不是异常
- 做总结或交接时，优先写“最终文件状态 + 已验证结果”，不要把中间尝试、临时误判或过时目录状态混成最终结论
